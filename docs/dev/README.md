# Dev harness for `docs/js/core`

Not part of the site (nothing links here), but it lives under `docs/` so the same static server serves it. Everything is
local: no network beyond a relay you start yourself. All pages import the core with relative paths, so serving `docs/`
under `/<repo>/` (as GitHub Pages does) works: `dev/headless.mjs` serves it under `/simple-screensharing/` to prove that.

## Files

| file | |
| --- | --- |
| `tests.html` + `tests.js` | 33 unit tests (run in the browser). Cross-language vectors from `vectors.json` |
| `vectors.json` | generated by a throwaway Rust program that depends on `protocol/` and the client lib by path (see "Vectors") |
| `live.html` + `live.js` | one peer joining a real relay: `role=share` (synthetic test pattern through the real encode path) or `role=view` |
| `pattern.js` | the synthetic capture source: noisy rectangles + a 40-bit frame-counter/clock strip + optional 440 Hz tone |
| `scenarios.html` + `scenarios.js` | 17 behaviour scenarios against a real relay (reconnect, room full, loss, nonce exhaustion, ...) |
| `probe.html` | what WebCodecs can decode/encode in this browser |
| `headless.mjs` | static server + headless Chromium runner (zero npm deps, Node >= 18) |
| `matrix.mjs` | browser sharer -> relay -> browser (or native) viewer for a codec x fps matrix |
| `native.mjs` | native sharer (external Rust program) -> relay -> browser viewer |
| `scenarios.mjs` | runs `scenarios.html`, restarts the relay when the page asks |
| `relay.sh` | start/restart/stop a throwaway relay in tmux and print its certificate hash |
| `pagelog.js` | page -> runner reporting (`/log`, `/result`, `/kv`) |
| `cdp.mjs`, `e2e-lib.mjs`, `e2e/`, `motion.html` | drive the REAL site UI and the native app end to end (see "End to end") |

## Running

```sh
# 1. unit tests (no relay needed)
node docs/dev/headless.mjs run dev/tests.html            # --out result.json keeps the JS-made reverse vectors

# 2. a relay (build your own copy; its TUI needs a pty, relay.sh uses tmux)
cargo build --release -p simple-screensharing-server && cp target/release/simple-screensharing-server /tmp/relay-bin
docs/dev/relay.sh start /tmp/relay-bin /tmp/relay-run 14433      # prints PORT=14433 HASH=<certhash>

# 3. scenarios, throughput matrix, native interop
node docs/dev/scenarios.mjs --relay 127.0.0.1:14433 --hash <HASH> --relay-bin /tmp/relay-bin --relay-dir /tmp/relay-run
node docs/dev/matrix.mjs --relay 127.0.0.1:14433 --hash <HASH> --codecs h264,av1 --fps 60,120,240 --size 1920x1080 \
     --duration 10 --flag --disable-frame-rate-limit --flag --disable-gpu-vsync
node docs/dev/native.mjs --relay 127.0.0.1:14433 --hash <HASH> --bin <nativesharer> --codec h264 --backend va --fps 60 --size 1920x1080 --audio
docs/dev/relay.sh stop 14433
```

* `--flag --disable-frame-rate-limit --flag --disable-gpu-vsync` matters: without it headless Chromium's compositor ticks at
  60 Hz, which caps `canvas.captureStream` at 60 fps and makes every 120/240 fps number meaningless.
* Chromium launches headless by default. `HEADED=1` shows real windows (needed for GPU video decode: headless GPU paths crash
  in this environment, `GPU process exited unexpectedly: exit_code=139/8704`); the runner refuses unless `SSS_GUI_LOCKED=1` is
  set, which you only do while holding the shared desktop lock (`flock` on `/tmp/claude-1000/sss-gui.lock`) with focus on a free monitor.
* Do **not** pass `--use-fake-ui-for-media-stream` for `getDisplayMedia` tests: it made Chromium pick a `screen:0:0` source.
* GPU decode needs `--flag --enable-features=VaapiVideoDecoder,VaapiIgnoreDriverChecks,AcceleratedVideoDecodeLinuxGL --flag --ignore-gpu-blocklist`.
  Chromium 153 on this machine has **no** hardware *encode* path for WebCodecs (all `prefer-hardware` encoder probes fail),
  so browser-side encoding is software (OpenH264, libaom/SVT-AV1).

## End to end through the real UI and the native app (I20)

`cdp.mjs` is a zero-dependency Chrome DevTools driver (click, type, eval, screenshot, console/network capture, headed or headless);
`e2e-lib.mjs` wraps the real site UI with it (create/join a room, stub `getDisplayMedia` with the harness pattern source, Go live,
Watch, measure); `e2e/` holds the runs: `sharer.mjs` / `viewer.mjs` / `viewer-headed.mjs` (browser peers with a file-based command
channel), `full-room.mjs`, `links.mjs`, `ui-reconnect.mjs`, `browser-to-browser.mjs`, plus `native-session.sh` (one short GUI-locked
session: scratch `XDG_CONFIG_HOME` seeded with the room, the native app on DP-1/DP-2, ydotool clicks, grim screenshots, clean teardown
incl. orphan `ssshare-loopback` pw-loopbacks) and `e2e/steps/*.sh` (the click sequences; coordinates are for the 1900x1060 tiled window).
`motion.html` is full-window moving content for portal captures. Needs: `E2E_OUT` (scratch dir, default `/tmp/sss-e2e`, keep it small),
`NATIVE_BIN`, `RELAY_BIN`/`RELAY_DIR`. Never run headed without the GUI lock; never put a picker screenshot on a full output.

Serve `docs/` and open `http://127.0.0.1:<port>/simple-screensharing/` (`node docs/dev/headless.mjs serve --port 8123`): the site and
every module load with no 404 and no console error from page code in all runs below. Chromium's own `ERR_QUIC_*` console errors
appear only while a relay is deliberately down (the CDP driver lists them separately as `browserNetErrors`).

Results (this machine, Chromium 153, relay + native client built from this branch, 1080p, noisy test content):

| scenario | result |
| --- | --- |
| 1a browser (real UI, harness capture + tone) H.264 60 -> native egui | pass: tile via `vah264dec` (hardware), tooltip "Decoded 60 fps shown 60 fps 0 dropped", 11.7 Mbps, audio sink-input created by the app |
| 1b same, AV1 | pass: `vaav1dec`, decoded 60 / shown 60, 8.0 Mbps, audio |
| 2a native (real portal picker, Spotify per-app audio) H.264 60 -> browser | pass: 59.9 decoded fps (headless, software decode), 0 loss, 0 decoder errors; audio 50 packets/s decoded, level > 0 |
| 2b H.264 120 | pass: 119.9 fps |
| 2c AV1 60 / 120 | pass: 59.9 / 120.0 fps (the native AV1 stream declares 1920x1082) |
| 2d H.265 60 (headed Chromium, VAAPI decode) | pass: 60.1 fps, 8.4 Mbps; headless cannot decode H.265 |
| 3 room full (9th member) | pass: the UI shows "This room is full (8 people at most)" (`JoinRejected{RoomFull}` on the control stream) |
| 4 relay restart | browser: reconnecting at 0 ms, joined again after 0.6 s, share kept live; viewers re-watch by `stableKey`. **Native does not reconnect by itself** (stays on "Not connected"); manual Connect + Watch works |

Audio level: Spotify runs at 10 % stream volume (-60 dB), so the captured signal peaks at about 0.0005 (`maxLevel` over 8 s); the packets
are real Opus frames of that quiet signal. `level` is a peak meter with a ~0.5 s hold; the first version reported one frame's instant peak.

Findings outside the website (not fixed here):

* **Native sender frames of a rotated output are rotated.** DP-2 is configured `rr:2` (180 degrees) in mango; a portal capture of it
  arrives 180 degrees rotated in every viewer (`VideoFrame.rotation` is 0, the pixels are rotated; DP-1 arrives upright, the native
  viewer shows DP-1 upright). The native pipeline ignores the PipeWire `VideoTransform` meta.
* **A killed or closed native app stays in the room for about 60-75 s** (the relay's idle timeout): no `Leave` / close on SIGTERM or window close.
* The native app does not auto-reconnect after a relay restart (see scenario 4).

## Vectors (Rust -> JS and JS -> Rust)

`vectors.json` is produced by a Rust program (kept outside the repo) that uses the real `protocol` crate and the real client
`net`/`fragment` code: every `ClientToRelay`/`RelayToClient` variant as postcard hex, both fixed headers, ten
encrypt+fragment cases (empty payload, one byte over a fragment, exactly two fragments, `u32::MAX` counter, 600-byte datagram
cap, ...), three previews, 23 join-link strings classified by the real Rust parser, and 18 codec-sniff / codec-string cases
(real x264/x265/VA/SVT/libaom output, strings computed by the Electron sidecar's Rust code).
`tests.js` asserts JS reproduces the ciphertext/datagrams byte-exactly and decodes the Rust bytes. In the other direction the
test page also emits JS-made frames/previews/control messages/links (`reverse`), and the same Rust program decrypts,
reassembles and parses them: `RUST VERIFIED 20 JS-produced vectors`.

Browser sharer -> relay -> browser viewer, synthetic noisy pattern (a worst case for encoders), 8 Mbit/s unless noted, no datagram loss.

40 ms jitter-buffer floor).

| --- | --- | --- | --- | --- | --- |

| H.264, VAAPI decode (headed) | | 119.6 (74 ms) | 186 (74 ms) | | |

| AV1, VAAPI decode (headed) | | 117.7 (79 ms) | 111.7 (89 ms) | | |
| H.265 | not encodable in this Chromium (no hardware encoder, no software one) | | | | |

The table is from runs on a quiet machine. The same matrix re-run at load average ~12 (other workers building/testing) gave, as
decoded fps at 60/120/240: H.264 60 / 89 / 46 and AV1 60 / 54 / 16 (viewer p50 82 ms .. 1.3 s): both software codecs are CPU-bound, so
expect large run-to-run variation on a busy machine. The matrix prints `load1` per row.

Everything above 60 fps is limited by the browser's **software encoder** (and, on a loaded machine, by software decode) (the capture source delivered the full requested
rate, `captured == generated`), not by the transport, relay, decryption or decoder: 0 lost frames, 0 decoder errors, `txDropped` 0
in every run. Real screen content is far cheaper to encode than this noise.

Chromium delivers **no** frames from tab capture (nothing to composite), and with `--use-fake-ui-for-media-stream` `getDisplayMedia`
resolved a `screen:0:0` (display surface `monitor`) source that also yielded no frames: don't pass that flag, it picks a screen source instead of the tab.

## What Chromium cannot do compared with the native app

* **Codecs:** H.264 and AV1 encode (software); **no H.265 encode** (headless Chromium here; browsers expose HEVC encode only
  through a platform hardware encoder). H.265 **decode** works only with a hardware decoder (VAAPI worked headed).
* **fps:** no fixed cap in the core. `getDisplayMedia` frame rate is whatever the browser/OS capture path delivers (often 60;
  the `frameRate` constraint is a request); the software encoder tops out around 150-190 fps (H.264) and 90-110 fps (AV1) at
  1080p on a 12-thread CPU; 4K60 is not sustainable without a hardware encoder.
* **Encoder control:** no GOP size, no x264/VA quality level, no CQP (see the preset table in `js/core/README.md`).
* **Audio capture:** only what `getDisplayMedia({ audio })` offers, which depends on browser, OS and the chosen source.
  Verified here with real **tab capture** (headed Chromium, `--auto-accept-this-tab-capture`, `source=tab` in `live.js`): the
  audio track arrives as 48 kHz stereo 16-bit, was Opus-encoded and heard by the viewer (peak 0.40 of a 0.4-gain tone). Window and
  screen audio were not testable unattended (they need the portal/OS picker). No per-application audio picker like native's
  `pw-loopback` taps.
* **Capture is damage-driven:** a static screen delivers no frames at all (the core re-encodes the newest frame as the
  keyframe a new viewer needs). The real tab capture also changes size when the window does: the core reconfigures the encoder
  (2 reconfigures in the run below) and viewers follow from the new SPS.
* **Detection of a vanished relay:** a gracefully stopped relay is noticed at once (CONNECTION_CLOSE, relay task #29); a killed one only after the QUIC idle timeout (~21 s). See `js/core/README.md`.
* **Datagram size** is capped by `datagrams.maxDatagramSize` (1024 measured), which is why every sender uses 1000.
