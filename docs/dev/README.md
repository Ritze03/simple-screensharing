# Dev harness for `docs/js/core`

Not part of the site (nothing links here), but it lives under `docs/` so the same static server serves it. Everything is
local: no network beyond a relay you start yourself. All pages import the core with relative paths, so serving `docs/`
under `/<repo>/` (as GitHub Pages does) works: `dev/headless.mjs` serves it under `/simple-screensharing/` to prove that.

## Running

```sh
# 1. unit tests (no relay needed)
node docs/dev/headless.mjs run dev/tests.html            # --out result.json keeps the JS-made reverse vectors

# 2. a relay (build your own copy; its TUI needs a pty, relay.sh uses tmux)
cargo build --release -p simple-screensharing-server && cp target/release/simple-screensharing-server /tmp/relay-bin
docs/dev/relay.sh start /tmp/relay-bin /tmp/relay-run 14433      # prints PORT=14433 HASH=<certhash>

# 3. scenarios, throughput matrix, native interop
node docs/dev/scenarios.mjs --relay 127.0.0.1:14433 --hash <HASH> --relay-bin /tmp/relay-bin --relay-dir /tmp/relay-run
node docs/dev/matrix.mjs --relay 127.0.0.1:14433 --hash <HASH> --codecs h264,av1 --fps 60,120,240 --size 1920x1080 \
     --duration 10 --flag --disable-frame-rate-limit --flag --disable-gpu-vsync
node docs/dev/native.mjs --relay 127.0.0.1:14433 --hash <HASH> --bin <nativesharer> --codec h264 --backend va --fps 60 --size 1920x1080   # + --audio only in a test VM, see "No audio on the host"
docs/dev/relay.sh stop 14433
```

* `--flag --disable-frame-rate-limit --flag --disable-gpu-vsync` matters: without it headless Chromium's compositor ticks at
  60 Hz, which caps `canvas.captureStream` at 60 fps and makes every 120/240 fps number meaningless.
* Chromium launches headless by default. `HEADED=1` shows real windows (needed for GPU video decode: headless GPU paths crash
  in this environment, `GPU process exited unexpectedly: exit_code=139/8704`); the runner refuses unless `SSS_GUI_LOCKED=1` is
  set. Since 2026-10-14 headed Chromium runs **only inside the headless sway rig**, never on the user's desktop:
  `client/scripts/hs-rig.sh run -- env SSS_GUI_LOCKED=1 HEADED=1 node docs/dev/headless.mjs run dev/tests.html` (the rig's absolute
  `WAYLAND_DISPLAY` makes Chromium open its window on the rig's sway; checked 2026-10-14, 37/37 pass). `SSS_GUI_LOCKED` is just the
  historical name of the opt-in; the old shared desktop lock itself is gone (the rig needs none).
* Do **not** pass `--use-fake-ui-for-media-stream` for `getDisplayMedia` tests: it made Chromium pick a `screen:0:0` source.
* GPU decode needs `--flag --enable-features=VaapiVideoDecoder,VaapiIgnoreDriverChecks,AcceleratedVideoDecodeLinuxGL --flag --ignore-gpu-blocklist`.
  Chromium 153 on this machine has **no** hardware *encode* path for WebCodecs (all `prefer-hardware` encoder probes fail),
  so browser-side encoding is software (OpenH264, libaom/SVT-AV1).

## Loss and NACK runs (#111)

`live.html` results now carry `receiver.frozen` (`{stalls, totalMs, maxMs, pctOfTime}`: gaps > 150 ms between shown frames, including a
freeze that lasts to the end) and `receiver.nack` / `sender.nack` (`client.nackStats()`). A/B a peer with `&nack=0` (the kill switch
reads the page URL). Recipe used for the tables in `superdoc/features/website/nack-and-big-keyframes.md` "Selective retransmission in the browser":
a relay (own build, `relay.sh`), one UDP impairment proxy per browser leg (`lossproxy.py`, the #99/#104 throwaway that lives in the
task scratchpads: per-client upstream socket, JSON control file with `loss`/`delay_ms`/`ge`, per direction), then
`runPair({ relay: <sharer proxy>, viewerRelay: <viewer proxy>, extra: "&detail=2", sharerExtra: "&nack=0", viewerExtra: "&nack=0", ... })`.
`detail=2` (a static colour-noise texture) gives the field's ~1 MB IDRs; the plain pattern's IDRs are too small to show the problem.
A native peer in the rig joins the same way: take the join link from `hs-rig.sh status`, replace `host:port` by the proxy's.
Pitfall: at this machine's load the software encoder + the paced 1 MB IDR leave a ~400 ms gap per keyframe, so "frozen" has a floor
(5.8 s per 30 s at a 2 s GOP) that is not loss; compare with the no-loss run.

## Firefox (Gecko)

The user's browser is Floorp (Firefox engine), so the pages also run in the system `/usr/bin/firefox`: `BROWSER=firefox node docs/dev/headless.mjs run dev/tests.html`
(also `matrix.mjs` with `VIEWER_BROWSER=firefox`, `live.html?role=view` against any relay). Headless by default, with a throwaway profile under
`<repo>/target/ff-profiles` (never `/tmp`, never a real profile); `--flag pref=value` sets a pref in its `user.js`
(e.g. `--flag layout.frame_rate=240`); `HEADED=1` (rig only, same rules as Chromium) opens a real window on the rig's sway, which is what
gives a GPU/VAAPI decode path (`--flag media.ffmpeg.vaapi.enabled=true --flag media.hardware-video-decoding.force-enabled=true`).
No geckodriver/CDP needed: pages report back over HTTP like for Chromium. Facts found 2026-10-15 (Firefox 157): WebTransport with
`serverCertificateHashes` against the self-signed relay works; WebCodecs decode works (H.264, AV1, VP8/9; **no H.265**); the
`VideoEncoder` accepts H.264 in `isConfigSupported` but fails at the first `encode()` ("EncodingError: The given encoding is not
supported", no OpenH264 plugin in a fresh profile) and there is no `MediaStreamTrackProcessor`, so **Firefox cannot be the sharer**:
`xbench.mjs` and `matrix.mjs` encode in Chromium. `optimizeForLatency: true` costs Firefox's software decoder 3.5-5x (see
`superdoc/features/website/viewer-features.md` "Rendering above 60 fps"). Other workers load this machine (load average 15-40 seen): repeat a run that
shows odd dips before believing it.

### No audio on the host (2026-11-04)

Every driver here is **video only by default**: `e2e-lib.mjs` `stubCapture` defaults to `audio: false` (it was `true`, so `browser-to-browser.mjs`, `links.mjs`,

## Vectors (Rust -> JS and JS -> Rust)

`vectors.json` is produced by a Rust program (kept outside the repo) that uses the real `protocol` crate and the real client
`net`/`fragment` code: every `ClientToRelay`/`RelayToClient` variant as postcard hex, both fixed headers, ten
encrypt+fragment cases (empty payload, one byte over a fragment, exactly two fragments, `u32::MAX` counter, 600-byte datagram
cap, ...), three previews, 23 join-link strings classified by the real Rust parser, and 18 codec-sniff / codec-string cases
(real x264/x265/VA/SVT/libaom output, strings computed by the native client's Rust code).
`tests.js` asserts JS reproduces the ciphertext/datagrams byte-exactly and decodes the Rust bytes. In the other direction the
test page also emits JS-made frames/previews/control messages/links (`reverse`), and the same Rust program decrypts,
reassembles and parses them: `RUST VERIFIED 20 JS-produced vectors`.

## What Chromium cannot do compared with the native app

* **Codecs:** H.264 and AV1 encode (software); **no H.265 encode** (headless Chromium here; browsers expose HEVC encode only
  through a platform hardware encoder). H.265 **decode** works only with a hardware decoder (VAAPI worked headed).
* **fps:** no fixed cap in the core. `getDisplayMedia` frame rate is whatever the browser/OS capture path delivers (often 60;
  the `frameRate` constraint is a request); the software encoder tops out around 150-190 fps (H.264) and 90-110 fps (AV1) at
  1080p on a 12-thread CPU; 4K60 is not sustainable without a hardware encoder.
* **Encoder control:** no GOP size, no x264/VA quality level, no CQP (see the preset table in `js/core/README.md`).
* **Audio capture:** only what `getDisplayMedia({ audio })` offers, which depends on browser, OS and the chosen source.
  Verified here with real **tab capture** (headed Chromium, `--auto-accept-this-tab-capture`, `source=tab` in `live.js`): the
  audio track arrives as 48 kHz stereo 16-bit, was Opus-encoded and heard by the viewer (peak 0.40 of a 0.4-gain tone). Window and
  screen audio were not testable unattended (they need the portal/OS picker). No per-application audio picker like native's
  `pw-loopback` taps.
* **Capture is damage-driven:** a static screen delivers no frames at all (the core re-encodes the newest frame as the
  keyframe a new viewer needs). The real tab capture also changes size when the window does: the core reconfigures the encoder
  (2 reconfigures in the run below) and viewers follow from the new SPS.
* **Detection of a vanished relay:** a gracefully stopped relay is noticed at once (CONNECTION_CLOSE, relay task #29); a killed one only after the QUIC idle timeout (~21 s). See `js/core/README.md`.
* **Datagram size** is capped by `datagrams.maxDatagramSize` (1024 measured), which is why every sender uses 1000.

right clicks), headless Chromium and a throwaway relay. Four pages: Alice, Bob and Carol each share a synthetic screen (16:9, 4:3, portrait), Vera watches all three and shares too
(her page has `?fakeaudio=1`: every stream acts as if its sender shared audio, so the ring, the volume row and the card's "Audio" can be tested without creating an audio stream).
A room of its own near the end has two pages of one name, both sharing `Screen`, and a third watching (#127: a person is a connection).

```sh
docs/dev/relay.sh start /tmp/relay-bin /tmp/relay-run 14433            # prints HASH
node docs/dev/e2e/stage.mjs 127.0.0.1:14433 <HASH> --relay-bin /tmp/relay-bin --relay-dir /tmp/relay-run \
     [--old-relay 127.0.0.1:14434 --old-hash <HASH2>]                  # E2E_OUT=<dir> for the screenshots
```

`--relay-bin/--relay-dir` let it restart the relay (a popped-out stream and the stage window must come back, avatars are announced again); `--old-relay` is a second relay started with
`SSSHARE_AVATARS=0` (acts like an older relay: owner sees her own emoji, others the initial). `relay.sh` forwards every `SSSHARE_*` variable of its own environment into the relay's tmux session (`SSSHARE_AVATARS=0 docs/dev/relay.sh start ...` works); a plain `VAR=x tmux new-session ...` does not, because a new session takes the environment of the already running tmux *server*. 198 checks on 2026-11-04 (the whole run: I11 + Settings tabs + tile glide + the I10 webcam/PIP part below, all pass, with the relay restart and the old-relay part). Real pointer input has one catch: a click is press and
release on one element and the UI re-renders on every state change, so the harness retries a click whose target was replaced in between (`Watch`, the stage pop-out button).
Since #131 (2026-11-04) Webcam in picture is on by default, so the webcam section first checks that and switches it off on Vera's and Alice's pages for its tile-based checks, and the last section ("Layout menu settings are saved") opens one more page, sets Crop plus the four switches, reloads it and checks the menu and `settings.stage` in localStorage.
The Document Picture-in-Picture window (stream and stage pop-out) works in headless Chromium on a secure origin (`http://127.0.0.1`), so those paths are tested too. Not simulated:
the pointer leaving the window (CDP cannot move it out; a synthetic `mouseleave` on `<html>` is dispatched instead), a real frame-size change of a stream.
